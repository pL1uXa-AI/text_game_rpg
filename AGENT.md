# 🤖 AGENT.md — Text Game RPG: правила разработки, архитектура, память проекта

> **Читай первым перед любой работой.** Этот файл объясняет, как устроен проект, какие правила нельзя нарушать и как тестировать изменения. Он создан, чтобы между ИИ-сессиями ничего не терялось.
> Если проект меняется — **обнови этот файл** (новая сессия должна видеть актуальную картину).

## 🎯 ЦЕЛЬ ПРОЕКТА

Живая текстовая RPG с ИИ-рассказчиком: игрок пишет действия на естественном языке, локальная LLM (llama.cpp) генерирует ответы, мир живёт, **ничего не забывается** (гибридная память + карточки сущностей). Веб-приложение: FastAPI + vanilla JS SPA.

**Сменный рассказчик:** персону повествователя (промпт) можно менять/создавать/править/удалять — предустановленные + свои (таблица `narrators`).
**Сменные провайдеры:** основная модель (llama.cpp / Ollama / OpenAI-совместимый), эмбеддинги и реранкер (RouterAI / OpenAI-совместимый / выкл.) — глобально в `.env` и per-world в настройках UI.

> ⛔ **Железное правило: если три закона ниже нарушены — доработка не принимается.**
>
> Движок механики — НЕ игровой смысл. Он лишь ОБСЛУЖИВАЕТ рассказчика.

## 🏛 ТРИ ЗАКОНА АРХИТЕКТУРЫ (нарушение = доработка не принимается)

Любая игровая механика и любая плановая доработка обязаны пройти эти три фильтра. Если новая идея не вписывается — переформулируй её так, чтобы вписалась, либо не делай.

### 1️⃣ ТОЛЬКО универсальные механики (для всех жанров и тем)
- Код хранит ОБЩИЕ абстракции (состояния, HP/MP/золото/уровень/статы, инвентарь+вес, эффекты, флаги, время/погода, фракции/репутацию, квесты/цепочки, магазины/торговлю, крафт/станции, компаньонов/врагов, способности).
- Вшитые сущности (расы/классы/профессии/навыки) — лишь **справочники-подсказки**; творческие появляются через `race_change{name,bonus,passive}` / `class{name,skill}` / `profession{name,buff}`.
- НЕЛЬЗЯ зашивать «это фэнтези/это ретро/это техно» в логику движка как жёсткий жанровый закон. Исключения типа `_is_modern_world` — осознанные и минимальные (только контекст старта роли), обязательно с комментарием «почему».

### 2️⃣ Общие базовые возможности для удобства, отображения и базовой логики
- Код даёт инфраструктуру: `format_state`, справки-агрегаторы (`total_sell_value`, `can_craft`, `/economy` `/stats` `/map` `/inventory`), парсинг кривых ответов модели, валидацию.
- Это только чтение/отображение/проверка, никогда — принятие решений за мастера.

### 3️⃣ Код только ПРОВЕРЯЕТ возможность; мастер-рассказчик решает ВСЁ
- Код — «судья возможностей» (валидатор): нет золота/материалов/станции/профессии/веса → отказ с объяснением. Он не отказывает «потому что не по жанру».
- Прогресс и суть персонажа — творчество рассказчика: профессия/класс/титул/уровень/статы меняются ТОЛЬКО директивами (правило 19 промпта); авто-прокачки по XP/очкам/счётчикам НЕТ.
- Рассказчик всегда может разрешить действие или дофантазировать мир — код не блокирует.
- **Тест для любой доработки**: *«Код решает за мастера?»*. Если ДА → переводи задачу в «проверку возможности» (валидируй — решение оставляет мастер).

Эти три закона — **канон формулировок именно здесь**; в `README.md` (раздел «🎯 Философия дизайна (три закона игры)») они повторены сжато, и заголовки обязаны совпадать — следит тест `test_three_laws_identical_in_docs` (C11, аудит 38: раньше в двух документах разошлись и формулировки, и перечни справок закона 2). Планировать доработки без трёх законов НЕЛЬЗЯ.

## ⚠️ ЖЁСТКИЕ ПРАВИЛА (нарушение = сломанный проект)

1. **НЕ трогать запущенный llama.cpp** на `127.0.0.1:8080`. Он уже работает (модель `Ternary-Bonsai-8B-TQ2_0`, **n_ctx 8192 токенов**). Если нет — молча его не запускаем, сообщаем пользователю.
2. **НЕ трогать ChromaDB учебника py_docs** на `127.0.0.1:8000`. У игры **свой экземпляр**: порт **8001**, venv `data/chroma-venv`, данные `data/chroma`, коллекция `text_game_memory`.
3. **Секреты**: `EMBEDDING_API_KEY` (RouterAI), `MAIN_API_KEY`, `RERANK_API_KEY` в `.env` — **никогда не выводить** значение ключа в консоль/логи/ответы (показывать `***`/маску `••••••••`) — маскирует `routers/core.py::_mask_provider` (`KEY_MASK` в `config.py`). Наружу (в `/api/*`, в экспорт, в дамп) ключ уходит только маскированным: `GET /api/worlds/{id}` и ответ `POST .../providers` отдают замаскированный снимок (`_masked_provider_settings` + `_safe_world_row`, который маскирует и вложенный JSON `world.provider_settings` — A3, аудит 38: иначе ключ утекал «боковой дверью»); `db.world_dump` дополнительно **вырезает** `api_key` из JSON-дампа мира — см. правило 15.
4. **Суммарный промпт — много меньше контекста модели.** Стандарт: `MAX_TOKENS` (вывод) и `CONTEXT_TOKENS` (контекст мира) в `.env` = **2000 / 32768 (32k)** — под облачные модели (RouterAI и др.). Бюджеты памяти настроены в `.env` (`RECENT_TOKEN_BUDGET=2600 — запасной`, `SUMMARY_TOKEN_BUDGET=700`, `RAG_MEMORY_K=4`, `RAG_CANDIDATES=20`). **Не превышать n_ctx РЕАЛЬНОЙ модели**: локальная llama.cpp = 8192 — для неё уменьшать `context_tokens` per-world (ползунок «Размер контекста») или в `.env`. Оценка токенов: `config.est_tokens` (len/3.2).
5. **После любого изменения `backend/*.py` — перезапуск сервера обязателен**: убить старый процесс на порту 8002, затем `python -m uvicorn backend.app:app --host 127.0.0.1 --port 8002` (запускать из корня, с `-X utf8`). Тот же адрес обязателен и в `start_game.bat` — **наружу (0.0.0.0) не слушать**: авторизации в игре нет, а в `.env` живые ключи. С B2 (аудит 41) это защищено и самим launcher'ом: чужой `GAME_BIND` без `GAME_BIND_CONFIRM=1` = отказ запуска (подсказка «запусти с 0.0.0.0» из вывода убрана), `/api/admin/settings` отвечает только с localhost (`ADMIN_ALLOW_LAN` в `.env` — сознательное открытие, самой админкой не включается), а «дорогие» LLM/сетевые эндпоинты под rate-limit'ом (`ratelimit.SCOPES`; чужому адресу лимиты режутся в `REMOTE_FACTOR=4` раза).
6. Фронтенд (`frontend/`) отдаётся статикой через mount `/static` — правки видны после refresh, перезапуск не нужен. Оба HTML-роута (`/` и `/admin`, `routers/system.py`) отдаются с `Cache-Control: no-store` (D15) — так что обычный F5 достаточно; а вот `app.js`/`style.css` идут через `StaticFiles` с ревалидацией по `ETag`, и при **«поведённом» фронте всё же делай hard refresh**. ⚠ Правки Python — перезапуск сервера, правки фронтенда — нет.
7. **SQLite-схема** (`data/game.db`) — миграции только идемпотентные: добавить `CREATE TABLE IF NOT EXISTS` в `backend/db.py::_init_schema`. Не удалять БД без спроса. Идемпотентная **само-исцеляющая чистка** допустима и уже есть: `db.prune_orphan_rows()` при старте сервера убирает строки связанных таблиц у несуществующих миров (A8: `worlds.id` — AUTOINCREMENT, и после VACUUM/импорта дампа id может достаться новому миру, который «унаследует» карточки/лор удалённого). `DELETE /api/worlds/{id}` чистит **все** связанные таблицы (events/saves/turn_snapshots/entities/lore/graph_nodes/graph_edges) и начинается с чистки векторов в Chroma: при её отказе — 503, мир НЕ удалён (иначе SQLite-строки ушли, а векторы осиротели). Тот же класс с другой стороны закрывает `memory.sweep_orphan_vectors()`: при старте векторы сверяются с `db.world_ids()` и чистятся (инвариант 31).
8. **Эмбеддинги/реранкер — облачные RouterAI** (как в py_docs/rag): модель `qwen/qwen3-embedding-8b` (4096-dim, префиксы `"Passage: "` для документов, `"Query: "` для запросов), реранкер `voyageai/rerank-2.5` через `/v1/rerank`. Локальных эмбеддеров в проекте нет.
9. **Фоновые задачи** (память/карточки/сводки) — асинхронные, **не блокируют ответ игроку**. Защита от повторов: busy-множества `_cards_busy`/`_judge_busy`/`_master_busy`/`_enemy_ai_busy`/`_event_busy`/`_vision_busy` — `backend/routers/core.py` (НЕ в app.py: с сессии 11 app.py — только сборка). Очередь, приоритеты, барьер перегенерации, «мир в ходу»/откат и «огонь-и-забыл» задачи — `backend/bg.py` (`bg.submit`, `bg.spawn`, `bg.regen_block`, `bg.rewind_block`, `bg.turn_block`, `bg.player_turn`).
10. Все файлы — **UTF-8**; Python запускать c `-X utf8` (Windows кодировка cp1251 ломает кириллицу).
11. **Судья логики — фоновый** (LLM-as-a-Judge), как архивариус: НЕ синхронный, НЕ переписывает ответ, не «душит» креативность. Две задачи: (а) противоречие жёстким фактам (мёртвый NPC / флаг) → системное сообщение-«искажение реальности» (сюжетный поворот, ошибка ИИ = фича мира); (б) **согласованность биографии и роли** (раса/класс/профессия/навыки/уровень) → если найден грубый конфликт, выдаёт `corrections`, которые применяются через движок директив (системное сообщение о правке). Глобальный выключатель `LOGIC_JUDGE_ENABLED` (.env/админка), per-world `gen_settings.logic_judge` (настройки мира), частота `LOGIC_JUDGE_INTERVAL`.
12. **Гарантия роли на старте**: `apply_character` контекстно-зависимый — для «современных»/реал/литрпг-миров (`_is_modern_world`) не форсирует фэнтезийный класс, ставит расу «Человек» и профессию «Безработный» при пустых полях; для фэнтези — класс по лучшему стату.
13. **Парсинг `game_engine({...})` текстом**: в tools-режиме модель иногда «выпевает» вызов вместо настоящего `tool_call` — `split_engine`/`find_engine_start` распознают `<<ENGINE>>`, `game_engine({...})` и голый JSON-блок, **в том числе втавленный в середину абзаца**, вырезая механику из видимого текста (сессия 36, п.4: единый сканер с балансировкой скобок вместо «от маркера до конца строки»). `engine_tail_hold` не даёт стриму показать обрывок маркера.
14. **Не глотать ошибки в фоне молча (сессия 19)**: в любых фоновых/асинхронных задачах (память, карточки, сводки, судья логики, динамические события, TTS) избегать тихого `try/except: pass` — логировать через `logger` (модуль `textgame`) с `logger.exception(...)`/`logger.warning(...)` и контекстом (world_id, seq, действие), чтобы диагностика не терялась. То же относится к «тихим» `return None` на горячем пути: сбой загрузки персоны рассказчика и исчезновение мира у фонового агента пишутся в лог (A19, аудит 38). **A6 (аудит 41) закрыл остаток: у фоновых `generate_*` (событие/мастер/боевой ИИ/видение/описание куба) отказ пишется через `narrator._agent_quiet()` — это `log_once` с ключом (`агент`, `world`) и traceback-ом, поэтому молчание исключено, но лог-шторм на каждом ходу тоже (агент живёт каждый ход, а при лежащей модели падает КАЖДЫЙ проход); два мёртвых замыкания `_parse()` (divine/logic_judge, не вызывались нигде) удалены, `db.close()` пишет warning при незакрытом соединении/цикле (залоченный `game.db` на Windows), а отказ rate-limit виден в журнале с ключом. Хелперов `quiet()`/`log_debug_once()` в `logsetup` НЕТ и не заводились — docstring модуля это обещание снял (тест сторожит).** Исключение — легальные фолбэки (RAG при выключенных эмбеддингах — ожидаемое поведение, а не ошибка; сама недоступность RAG логируется, сессия 33).
15. **Git и секреты (сессия 33)**: репозиторий `github.com/pL1uXa-AI/text_game_rpg` — **приватный**. В git НЕ попадают: `.env` и любые `.env.*` (живые ключи), вся папка `data/` (744 МБ: game.db, chroma, chroma-venv, tts, fastembed, backups, metrics.jsonl, logs/), логи, `nul`, `__pycache__`. В репозитории — код, документация, `plots/` и `.env.example` (шаблон без ключей). Перед каждым пушем проверять: `git diff --cached | grep -ciE "sk-[A-Za-z0-9]{12,}"` → **0**. JSON-дамп мира (`/export/json`) обязан быть без ключей (тест `test_world_dump_strips_api_keys`). Мусор рабочей копии (`.env.bak*`, `nul`, `server*.log`, `data/fastembed_test/`, `scripts/_test_repair.py`) удалён в сессии 39 по решению владельца — но это **не обещание навечно**: такие файлы **могут появляться локально** снова и это не баг доков (`nul` плодит любое `>nul`/`> nul` в `.bat` — `start_game.bat:10,94`, `scripts/setup_env.bat`; `server*.log` — ручной перезапуск сервера с перенаправлением вывода). **Рабочее дерево — не объект проверок**: тест `test_b1_trash_files_stay_out_of_git` сверяет **индекс git**, а не файлы на диске, и никогда не утверждает, что рабочее дерево чисто; за правдой о дереве следят `tests/test_session57_worktree_trash.py` (канон мусора покрыт `.gitignore` + правило 15 честно признаёт локальное существование таких файлов). **Удалять их — только по явному разрешению владельца**: это его рабочие файлы (и их логи), а `nul` на Windows снимается лишь `del \\?\D:\...\nul` — обычный `rm`/`del` его не видит.

## 🧠 АРХИТЕКТУРА (понимание проекта)

### Поток одного хода игрока
```
POST /api/worlds/{id}/action[/stream]
  → db.add_event(player)
  → 🕐 начало хода (routers/core.py): tick_effects (HP/MP ×стаки, turns−1, отсчёт «⏳ … осталось N ходов")
    + tick_needs_mental + tick_world_timers + tick_time (авто-часы: утро→день→вечер→ночь,
    сессия 40 п.14b); всё — в tick_msgs: уходят системками в чат И в контекст рассказчика
    («[Начало хода] …»), при перегенерации тикаются только после отката к снапшоту
  → narrator.retrieve_memory()        # RAG: Chroma → hybrid BM25 → rerank
  → narrator.select_relevant_entities() # карточки сущностей (приоритетная выдача)
  → _recent_block(exclude_ids=…)       # недавняя ИСТОРИЯ без событий текущего хода
    # A3 (аудит 41): действие уже записано в БД и ОДНОВРЕМЕННО идёт в [ДЕЙСТВИЕ ИГРОКА];
    # без фильтра модель читала его дважды (дубль съедал recent_token_budget и провоцировала
    # копирование своей формулировки). При ↻ отсекаются и прежнее действие, и replaced_ids.
    # ИНВАРИАНТ: любой новый блок промпта из «своего» события хода обязан попасть в exclude_ids.
  → narrator.build_messages()          # system prompt + сводки + RAG + карточки + recent + действие
  → llm.stream_chat() / llm.complete() # llama.cpp
  → narrator.split_engine()            # вырезает <<ENGINE>>{...} из ответа
  → narrator.apply_directives()        # применяет механику к setting; возвращает системные сообщения
  → если directives["roll"]: roll_expr() + narrate_roll() (второй LLM-проход)
    # roll_expr клампит ввод (A1, аудит 41): count ≤ 100, 2 ≤ sides ≤ 1000, |mod| ≤ 1000;
    # «ноль кубиков»/d0/d1/нераспознанное → фолбэк d20 + log.warning, ход НЕ падает (без 500).
    # roll_outcome (D7, аудит 41) судит по ФАКТУ броска, а не по написанию/итому: nat-1 — это
    # грань из res["rolls"] (одинокий кубик, выпала 1 — крит-провал даже с mod +5), форма куба
    # читается из той же регулярки, что и распознавание (_dice_shape: `d20` = `1d20` = `D20+3`),
    # планка «провал на 10+ хуже dc» — только у одиночного d20.
  → db.add_event(narrator [+ dice + system])
  → db.update_world(setting)
  → narrator.ensure_knowledge_cards()  # карточки знаний (раса/класс/профессия/навык/эффект) — инлайн
  → TTS-озвучка (если включена): событию ставится tts_status=1, фоновый синтез tts.ensure_event_audio (кэш + файл)
  → 📈 метрики хода (`metrics.record`) — в памятный БУФЕР, диск на горячем пути не трогается
    (D14, аудит 41): data/metrics.jsonl дописывается ПАЧКАМИ (по объёму `_FLUSH_BATCH` или
    «разрядкой» по возрасту `call_later`), в потоке, а остаток дочитывается `finally`-`_lifespan`;
    `METRICS_PERSIST=false` (conftest) — буфер даже не заводится; формат журнала не менялся
  → фоновые задачи: index_exchange, updatesummarize_and_compress, update_entity_cards, index_entities(знания)
  → ⚖️ судья логики (фоново, по интервалу ходов): сверяет ответ с критичными фактами мира;
    найденное грубое противоречие оформляется системным сообщением-«искажением реальности» (сюжетный поворот)
    # ВСЕ фоновые агенты (судья/мастер/боевой ИИ/видение) зовут свой LLM-проход на
    # ПЕРЕЧИТАННОМ из БД состоянии `s`, а не на снимке хода `agents_setting` (A4, аудит 41:
    # судья брал аргумент → вердикт по фактам прошлого хода = ложные «искажения»).
    # Знак `…` в сигнатурах ниже = `action, reply` (последний обмен), а НЕ состояние: у этих
    # агентов параметр `setting` — остаток до-А4 эпохи, он в расчёте не участвует (D6, аудит 41).
    # Динамическое событие — единственная задача, которой мир вообще не передаётся:
    # `_maybe_dynamic_event(world_id)` перечитывает его сам, снимка хода у неё нет.
  → 🌍 динамическое событие (фоново, по шансу на ход, `event_chance`): случайный сюжетный
    поворот мира («🌍 …») + директивы — `routers/core.py::_maybe_dynamic_event(world_id)`
  → 🤖 автономный «мастер» (фоново, по интервалу ходов): при «застревании» игрока (повтор действий / без
    активных квестов) генерирует квест/сюжетный поворот («🤖 Мастер: …») и применяет директивы
  → ⚔️ боевой ИИ врагов (фоново, по интервалу ходов, пока есть живые враги): выбирает их тактический ход
    (преследование/охрана/отступление/переговоры/ловушка) — не дублирует урон игроку, ставит ai-намерение
```

### Директивы `<<ENGINE>>` / function calling (механика через LLM)
Механика передаётся двумя способами, выбирается автоматически:
- **tools (function calling)** — облачные `main_provider=openai_compat` (RouterAI и др.): сервер шлёт инструмент `game_engine` (см. `narrator.py::GAME_ENGINE_TOOL`), директивы приходят как `tool_calls` (JSON аргументов). В контекст не попадают `<<ENGINE>>` — маркер не появляется в выводе (фильтр строк в `build_system_prompt` при use_tools).
- **промпт-формат `<<ENGINE>>`** — локальные llamacpp/ollama: модель пишет маркер по правилам промпта.
Принудительный фолбэк-аудит: если tools-режим дал текст без механики, а действие её явно требует (`narrator.mech_trigger`), выполняется компактный проход с `tool_choice:required` → JSON дельт на основе текущего состояния + последнего обмена (`narrator.audit_messages`). Парсинг: `llm.stream_chat/complete(..., tool_calls_out=...)` собирает вызовы; `narrator.parse_tool_args` нормализует вложенные JSON-строки и «голые» дельты.

Поддерживаемые директивы (см. `narrator.py::apply_directives`):
- `roll: {expr, mod, dc, label}` — бросок d20/d100 (результат описывает второй проход модели)
- `player: {hp, mp, gold, xp, level}` — урон/лечение/золото/опыт. Уровень растёт ТОЛЬКО явной директивой `level` (ритуал/испытание/дар — творчески, на рассказчике); XP копится как информация без автопрокачки по порогу; через recalc_derived
- `player.stats: {"сила": 2}` — статы игрока аддитивно (мин. 1); майоры статов
- `player.actions: {"кузнечное дело": 1}` — накопление действий (прогресс профессий, см. PROF_ACTION_MAP); **смену профессии решает рассказчик** директивами `profession` (авто-мена отключена, см. сессию 19)
- `race_change: "эльф"` (или `{name, bonus, passive}`) — раса: вшитая или творческая; снятие старого бонуса/пассива (`_apply_race_change`)
- `class: "Воин"` (или `{name, skill}`) — класс: вшитый со стартовым навыком или творческий со своим `skill`; `class_rank`, `class_evolve`, `secondary_class`, `secondary_rank` — ранг/эволюция/мультикласс
- `profession: "Кузнец"` (или `{name, buff}`) — профессия с постоянным баффом стата (снятие буффа старой)
- `skill_add: {name, rank, kind, desc, mp_cost}` / `skill_rank` / `skill_remove: name` — навыки с рангами F..G (`RANK_ORDER`), старый формат `skill {name, value}` конвертируется
- `title: "Ветеран"` / `reputation: {"гильдия воров": 2}` — титулы и репутация (аддитивная). **Ступень репутации** (`mechanics.reputation_standing`) — ярлык доверия фракции: Изгой(<−100)/Заклятый враг(≤−12)/Враг(≤−5)/Недоверие(≤−1)/Нейтрально(≤1)/Доверие(≤5)/Друг(≤12)/Союзник. **Разлив по связям**: если фракция объявлена в `setting.factions` с `relations` (союз/враг), изменение репутации передаётся союзникам (1/4 выгоды) и врагам (−вся дельта).
- **Фракции → геймплей (сессия 23)**: `faction_add: {id, name, desc, alignment, relations: {other: союз|враг}}` (создать/обновить) / `faction_update` (править существующую) / `faction_remove: id`. Фракции хранятся в `setting.factions` (id → {name, desc, alignment, relations}); `reputation` и `npc.faction`/`shops.faction` используют один и тот же id. Правило 26 промпта: рассказчик ведёт реакцию/диалог/квесты NPC строго по ступени игрока у фракции NPC. UI: вкладка «Состояние» показывает репутацию со ступенями и блок «🏴 Фракции» со связями; в модалке NPC отображается фракция + ступень.
- `effect_add: {name, turns, damage, heal, mp_damage, mp_heal, kind, stacks, mods, desc, tag}` / `effect_remove: name` — эффекты; автотик в начале хода (урон/лечение ×стаки, turns−1), `turns:-1`/без = постоянно; `mods` — моды статов (видны в `effective_stats`, базу не меняют); `tag: race/profession` — пассивки рас/профессий. Авто-тик включается глобально `TICK_EFFECTS_ENABLED` (.env/админка, по умолч. true) — при `false` эффекты не тикают сами, урон/лечение ведёт рассказчик директивами `player.hp`.
  (эссе п.1 — в `AGENT_ARCHIVE.md`, «Сессия 40, п.1»: почему у эффекта появился
  второй тикающий ресурс, MP)
- `add_item / remove_item: [{name, qty, desc}]` — выдача/снятие предмета (всегда с `desc`).
  **D9 (аудит 41): `value`/`weight` предмету пишет ОДНА точка — `mechanics._give_item`** (у неё же
  их берут `trade_buy`/`gather`/`craft`), а не вторичным поиском по инвентарю после выдачи; и
  **системное сообщение одно на ход**: «🎒 Получено: Меч ×1000; Щит ×200» (предметы с одинаковым
  именем склеиваются, больше 6 имён сворачиваются в «… и ещё N») — раньше «выдай 1000 мечей»
  (длинный список в `add_item`) давал 1000 строк в чате.
- `item_update: {name, desc, new_name, weight, value, note}` — **правка уже выданного предмета** (сессия 40, п.2): `add_item` чужое `desc` не трогает, поэтому закрепить описание найденного предмета можно только этой директивой; `desc` дописывается, а не затирается, нет предмета → «⚠ Нет предмета …». Предмет без описания показывается как «(описание не известно)» — чтобы модель видела пробел и закрыла его (правило 18а, ключ в `GAME_ENGINE_TOOL`, audit-промпте и промпте Провидения). Полное эссе: `AGENT_ARCHIVE.md`, «Сессия 40, п.2».
- Экономика: `shop_add: {id, name, owner, faction, items: [{name, price, qty, value, weight, desc}]}` / `shop_remove` / `shop_update`; торговля `trade_buy: {shop, item, qty}` (списывает золото, минус запас) / `trade_sell: {shop, item, qty}` (начисляет по `value` предмета). Цены автоматически корректируются репутацией фракции магазина (`player.reputation[faction]`, ±5%/ед., потолок ±50%). У предметов — `price` (покупка), `value` (продажа) и опционально `weight` (кг). Купленный предмет наследует `value`/`weight` из ценника магазина.
- **Вес предметов и вместимость (сессия 28)**: предметы могут иметь вес `weight`; рюкзак ограничен `carry_capacity(p)` = 20 + сила×2 + выносливость×2 (по статам, значит всегда актуально и для старых сохранений). Текущая загрузка `inventory_weight(p)` = Σ weight×qty. Покупка/сбор/создание предметов с весом, не помещающихся в запас, **автоматически отклоняются** («🎒 Перегруз: не хватает …») — у крафта проверка ДО списания ингредиентов (фигня не списывается). `add_item` (сюжетная награда) вес хранит, но не блокируется. Показ: «🎒 Загрузка: N/Банк» в `format_state` и в UI сайдбара/карточек (`inventory_weight`, `carry_capacity` в `mechanics.py`).
- Крафт: `craft_learn: {id, name, ingredients: [{name, qty}], result: {name, qty, value, weight, desc}, profession, station}` (учить рецепт) / `craft_remove` / `gather: {item, qty, weight}` (собрать ресурс) / `craft: {recipe, qty}` (создать — ингредиенты списываются, нехватка/перегруз → отказ). Рецепты в `setting.crafts`.
- **Станции и профессия для крафта (сессия 28)**: рецепт может требовать мастерскую `station` (название или список) и/или `profession`. Станция задаётся мастером в локации (`location_add/update {stations: [...]})`) или флагом `station:<имя>=true`; доступность проверяет код (`location_stations`/`has_station` в `mechanics.py`) — при отсутствии нужной станции/профессии создание отклоняется с явным сообщением. Мастер всегда может дать профессию (`profession`) или «обустроить» место (`station`). Это базовая логика-проверка возможностей, решает мастер.
- **Справки экономики (сессия 28, только отображение)**: `total_sell_value(player)` — сколько можно выручить, продав весь инвентарь; `/economy` (и алиасы `/shops`, `/craft`) — сводка: золото, загрузка рюкзака, сумма продажи, локальные станции, список магазинов и сколько рецептов сейчас можно создать. В состоянии рассказчика показываются «💰 Продажу/сделки», «📕 Станции здесь» и (для магазинов) цена продажи/вес товаров.
- Компаньоны: `companion_add: {id, name, hp, max_hp, level, skills, loyalty, faction, desc}` (добавить спутника) / `companion_remove` / `companion_update: {id, level, loyalty, name, desc, faction, skills}` / `companion_apply: {id, hp}` (урон/лечение с ограничением до max_hp, HP≤0 — пал). Спутники в `setting.companions`.
- `enemy_apply: {id, hp}` / `enemy_add: {id, name, hp, dmg, desc, money}` / `enemy_remove`. У врага может быть кошелёк `money` — при победе (enemy_apply до 0 HP) золото из кармана автоматически переходит игроку.
- **Живой мир / отход от канвы (сессия 63)**: `quest_remove: id | [id...]` — стереть квест, который **стал невозможен** (не «выполнен»/«провален»; снимает и привязанный дедлайн, не трогает `progress.quests_done`); `location_remove: id | [id...]` — мир теряет место (чистит входящие `connections`; **текущую локацию игрока удалить нельзя** — рассказчик обязан сперва сделать `move`, это «код проверяет»); `world_evolve: {what, why}` — явная отметка мастера «сюжет свернул с написанной канвы», хранится в `setting.plot_deviation` (кап 20), показывается в состоянии блоком `🧭 ЖИВОЙ МИР (ход N; активные арки: …)` и возвращается в промпт следующего хода — иначе через 30 ходов канва в промпте начнёт спорить с реальностью. Модуль `backend/plot_deviation.py` (чистое хранение, закон 2), обработчик `mechanics.PlotDeviationHandler`. Правило **37** в `narrator_data.TAIL_RULES` («ЖИВОЙ МИР vs КАНВА СЮЖЕТА»): сюжет/`quest_chains` — точка отсчёта, не обязательный путь; правило намеренно **не** внесено в `_GATED_RULES` (это не подсистема, нужно каждому миру). Стиль тем/сюжетов (`plots._theme_from_plot`, `narrator.theme_from_custom`, фолбэк `_world_theme`) переформулирован с «строго в русле сюжета → к финалу по канве» на «канва — напряжение, а не маршрут»: раньше именно эта строка делала стандартные сюжеты рельсовыми.
  *Последствие для бюджета промпта*: правило 37 стоит ~300 токенов, а каскад усечения (`build_messages`) на узких окнах вырождался (лор/RAG/карточки/сводки/история срезаны, переполнение остаётся) — добавлены два последних рычага: резка карточек **не из сцены** и удаление блока примеров `<<ENGINE>>` (`narrator.drop_engine_examples`, режет только строки с маркером, нумерацию правил не сдвигает). Закрыто тестом `test_build_messages_never_overflows_window`, который до этого был на грани (6192/6192 на HEAD).
  **Что НЕ показывается игроку** (с63, правка владельца): и блок `🧭 ЖИВОЙ МИР`, и сама запись
  отхода — только заметки мастера (как «🗝 Тайны» NPC): `format_state` зовётся из промптов агентов и
  в UI не попадает, а `PlotDeviationHandler` возвращает ПУСТОЙ список сообщений — строка «мир
  отходит от канвы сюжета» в чате выдала бы существование заранее написанного сценария и ломала
  бы иллюзию живого мира изнутри. **Лимита частоты в правиле 37 нет**: «раз в 10–15 ходов» убрано
  как искуственная клетка — счётчик хода в состоянии оставлен только как ориентир рассказчику,
  частоту поворотов он выбирает сам по сюжету (сторожится тестом `test_rule37_...`).
- `quest: {id, title, desc, status}` / `quest_done: id`; ветвление/ступени/цепочки (сессия 21): `quest_advance: {id}` — авто-вперёд по шагам `steps` или по имени, `quest_choose: {id, branch|chosen}` — зафиксировать выбранную ветку, `quest_done: {id, next}` — выполнить квест и сразу активировать следующий (цепочка 1→2→3; `next` может быть `{id, title}`)
- `ability_add: {name, school, cost, source, desc}` / `ability_update` / `ability_remove` / `ability_use: {name, cost}` — универсальные сверхспособности (магия/техно/псионика/навыки Системы), `use` списывает MP; правила 18а в промпте
- `progress_add: {победы: 1, …}` / `achievement_add: {name, desc}` — статистика пути и достижения (правило 20а); авто-счётчики kills/quests_done/discoveries/moves копятся кодом
- `npc_set: {id, name, mood, alive, desc, faction, schedule, money}` / `npc_kill: id`; `schedule` — опциональное расписание NPC по времени суток (`{ночь: "таверна закрыта", день: "рынок"}`); `money` — кошелёк NPC (показывается «🪙»), при `npc_kill` золото игроку и кошелёк обнуляется. Всё показывается в состоянии и в сайдбаре; правило 25 в промпте
- `location_add: {id, name, desc, connections: [id...], stations: ["кузница"]}` — опциональный список `connections` строит граф локаций (рёбра двунаправленные, если цель известна); опциональный `stations` (названия-мастерские локации) нужен для крафта со станциями (син.). Альтернативно флаг `station:<имя>=true` объявляет станцию в месте. / `location_update` (может править `stations`) / `move: location_id` — при перемещении переход запоминается как ребро между старой и новой локацией (карта мира, вкладка «Карта»)
- `flag: {name, value}`; `time: "ночь"`; `weather: "гроза"`; `game_over: true`. Время суток и погода дают геймплейные эффекты (`narrator.environment_mods` → «Влияние среды» в состоянии, правило 24 промпта); `npc_set.schedule` — расписание NPC по времени (правило 25). Универсально для всех жанров (не только фэнтези). **D8 (аудит 41): звено мира показывает запись — «🕐 Время: ночь», «🌦 Погода: гроза», «🚩 <title или ключ> — да/нет/строка»** (закон 2 — это только отображение, решение по-прежнему на мастере). Показывается ТОЛЬКО реальная смена: значение, равное текущему (сравнение в lower/strip), молчит — иначе ход авто-часов (`tick_time`, «🕐 Часы мира: вечер → ночь» в начале хода) давал бы дубль; молчат и служебные `station:`-флаги (машинный ключ, его игрок читает как «📕 Станции здесь»), и пустые/нулевые значения. `game_over` системки не даёт (её ведёт фронт и финальный чек).
- **Механики сессии 32 (универсальные)**:
  - `timer_add {name, turns, desc}` / `timer_remove` — **таймеры мира** (дедлайны: бомба/осада/прибытие) в `setting.timers`; движок тикает в начале хода, по истечении пишет «⏰ Таймер истёк» — ЧТО случилось решает мастер (правило 30).
  - `equip {item}` / `unequip {item}` — **экипировка по слотам** (`slot` у предмета: голова/торс/руки/ноги/оружие/вторая рука/аксессуар; `bonus {стат: +N}` — моды к `effective_stats`); код проверяет наличие предмета и занятость слота («судья возможностей»); «🛡 Экипировано» в состоянии/UI.
  - `needs {голод: {value: -10}}` — **потребности/рассудок** (`player.needs {голод/жажда/усталость}`, `player.mental {рассудок/стресс/мораль}`, шкалы с value/max/decay); тикают сами (`TICK_NEEDS_ENABLED`), предупреждают при критике; последствия ведёт мастер (правило 31).
  - `date {day, month, season}` — **календарь/сезоны** (`setting.date`); сезоны дают моды в `environment_mods`.
  - `location_add {..., effects: [...]}` — **локации-зоны** с постоянными эффектами: при входе эффект накладывается, при выходе снимается (`apply_location_effects`, «🌫 Влияние места»).
  - `board_add {title, text}` — **доска объявлений** (`setting.board`, чистое отображение, `/board`, блок в UI).
  - `faction_rank {faction, rank}` — **звания во фракциях** (`player.faction_ranks`): репутация = доверие, звание = должность.
  - `vision_add {text, hint}` — **видение в очередь** (`setting.pending_visions`); `POST /api/worlds/{id}/vision/trigger` разыгрывает отдельным LLM-проходом (сны/галлюцинации/сигналы, память как сюжет).
  - `roll.stakes {success, fail}` — **ставки на бросок**: показываются в сообщении кубов.
- Комбинируются: `"player": {"hp":-3}, "flag": {"name":"трап"}`

Фолбэк-парсер `_fallback_parse` — если LLM не вернул валидный JSON.

Нормализация типов (`str вместо dict`, числовой `id` → строка) — `backend/directives.py` (Pydantic-схемы директив): `narrator.normalize_directives` делегирует туда; семантика идентична прежней, закреплена золотым корпус-тестом (tests/test_directives_schemas.py).

**Применение директив через «Цепочку обязанностей»** (`backend/mechanics.py`): вместо одной гигантской `apply_directives` механика разбита на обработчики `DirectiveHandler` по группам директив — `PlayerHandler` (hp/mp/gold/xp/stats/actions+уровень), `IdentityHandler` (раса/класс/ранг/эволюция/мультикласс/профессия), `SkillHandler` (навыки/титулы/репутация), `EffectHandler` (эффекты), `ItemHandler` (инвентарь), `EconomyHandler` (магазины/торговля), `CraftHandler` (крафт/сбор), `CompanionHandler` (спутники), `EnemyHandler`, `QuestHandler`, `NpcHandler`, `FactionHandler` (фракции и связи), `LocationHandler` (карта/перемещение), `WorldHandler` (флаги/время/погода/game_over). Все собраны в `DIRECTIVE_CHAIN`; `apply_directives` прогоняет запрос по цепочке — каждое звено владеет непересекающимся набором ключей и обрабатывает только свои. Новая директива = новый обработчик (не правка монолита); сбой одного звена изолирован try/except и не роняет ход. Порядок сообщений сохранён.

### Боевой ИИ врагов (сессия 26)
Фоновый тактический агент, который даёт живым врагам собственный ход в бою. Запускается после каждого хода (как судья/мастер), вмешивается только когда в `setting.enemies` есть живые враги (hp>0).
- **`narrator._living_enemies(setting)`** — список живых врагов `[(id, enemy)]`, сортировка по убыванию `dmg` (кто опасный — решает первым).
- **`narrator.enemy_ai_messages` / `generate_enemy_ai(...)`** (`max_tokens=260`) — промпт и LLM-проход: по живым врагам, состоянию игрока (HP/статы/уровень, `effective_stats`) и последнему обмену выбирает ОДНО тактическое решение: `attack` (преследовать), `guard` (оборона/дистанция), `retreat` (отступить), `negotiate` (переговоры/сдача), `trap` (ловушка). JSON `{enemy, mode, note, directives}`.
- **`narrator._apply_enemy_ai(setting, eid, mode, directives)`** → применяет решение **без нанесения урона игроку** (урон игроку ведёт рассказчик в своём ходе — правило 9/9а; чтобы не задваивать). `retreat` убирает врага (`enemy_remove`, сообщение «🏃 … отступает»); остальные режимы пишут `enemy.ai = mode` (намерение-подсказка рассказчику на следующий ход) и применяют не-уроновые директивы (flag/npc/quest/add_item).
- **Фоновая задача** — `routers.core::_maybe_enemy_ai(world_id, …)` (`_enemy_ai_busy`), интервал `ENEMY_AI_INTERVAL`; системное сообщение «⚔️ …» + применение, индексация в память. Глобальный выключатель `ENEMY_AI_ENABLED` (.env/админка).

### Автономный «мастер» (сессия 25)
Фоновый сюжетный агент, который выводит игрока из тупика (`застрял»). Запускается после каждого хода (как судья логики), но вмешивается редко.
- **Детекция застревания** — `narrator.master_stuck_reason(actions, active_quests, turns)` (детерминированно, без LLM): `repetition` — в последних ≤6 действиях игрока ≥2 похожих (нормализация/стоп-слова + порог схожести); `drifting` — сыграно ≥15 ходов без единого активного квеста и ≥3 действий. При разнообразии и наличии квеста — `None` (мастер молчит). Вспомогательные `_action_similar`/`_norm_words` (нормализация, стоп-слова).
- **LLM-проход** — `narrator.generate_master_nudge(setting, reason, recent_text, lang, provider)` → `(текст, директива)`; `master_messages` (компактный промпт, `max_tokens=300`) просит ОДИН шаг (квест через `quest` / сюжетный поворот / слух / NPC-подсказку), не решать за игрока и не ломать лор.
- **Фоновая задача** — `routers.core::_maybe_autonomous_master(world_id, …)` (`_master_busy`), интервал `AUTONOMOUS_MASTER_INTERVAL` (ходов), не чаще; системное сообщение «🤖 Мастер: …» + `apply_directives`, индексация в память. Глобальный выключатель `AUTONOMOUS_MASTER_ENABLED` (в `.env`). Не блокирует ответ игроку.

### Динамическая сложность (сессия 24)
Сила врагов и частота случайных событий подстраиваются под уровень игрока (`player.level`), чтобы угроза не отставала от прокачки и мир не деградировал в сторону лёгкости.
- **`mechanics.dynamic_adversary_scale(player, difficulty, level=)`** — множители `{hp, dmg, event}`: на уровне 1 все = 1.0 (ничего не меняется); дальше рост за каждый уровень зависит от сложности мира (`_DYNAMIC_SLOPES`: easy/normal/hardcore) — хардкор растёт круче, лёгкая мягче. `event` растёт слабее (+5%/уровень).
- **Масштабирование `enemy_add`**: движок (`EnemyHandler`) берёт заданную рассказчиком БАЗОВУЮ HP/урон (нормальную для сеттинга/локации) и сам умножает на множители — поэтому сила врагов детерминированно растёт с уровнем, даже если LLM не учтёт прокачку.
- **Частота событий**: `narrator.event_chance(turns_since, every_turns, level=)` — шанс растёт и с ходами, и с уровнем (`freq = 1 + (level-1)*0.05`); потолок **0.5** («никогда не гарантировано») сохранён. `routers.core::_maybe_dynamic_event` передаёт уровень игрока.
- **Сигнатура агента события** (D6, аудит 41): `_maybe_dynamic_event(world_id)` — ОДИН аргумент. В отличие от судьи/мастера/боевого ИИ она не получает снимок состояния хода и не может по нему судить: мир и `setting` перечитываются из БД внутри задачи (там же, где проверка `_event_last_turn` и барьер `↻`). Правки этой строки в доке и подписи синхронны — сторожится `tests/test_session68_dynamic_event_signature.py`.
- **Подсказка рассказчику**: в `format_state` добавляется строка «⚖️ Сложность: … → враги HP×…, dmg×…, события ×…» с указанием задавать базовую силу; то же повторено в аудит-промпте боя.

### RPG-система (сессия 5)
- **7 статов** (10 = средний человек): сила/ловкость/выносливость/интеллект/мудрость/харизма/удача — `player.stats`, штраф ниже 1 запрещён. Производные: `max_hp` от выносливости, `max_mp` от интеллекта+мудрости (`recalc_derived`, не понижает максимумы старых сохранений).
- **Потребности/рассудок (сессия 32)**: `player.needs` (голод/жажда/усталость) и `player.mental` (рассудок/стресс/мораль) — универсальные оси ресурсов со шкалами `{value, max, decay}`; тикают сами в начале хода (`TICK_NEEDS_ENABLED`), предупреждают при критике; последствия (эффекты/штрафы) ведёт мастер директивами (закон 3, правило 31).
- **Экипировка (сессия 32)**: у предметов `slot` (голова/торс/руки/ноги/оружие/вторая рука/аксессуар) + опц. `bonus {стат: +N}`; `equip/unequip` надевает/снимает (`player.equipped {слот: имя}`), бонусы входят в `effective_stats`; код отказывает в двух предметах одного слота, нехватке предмета. Рассказчик даёт предметы с `slot` через `add_item`.
- **8 вшитых рас** (человек/эльф/дварф/орк/зверолюд/полудемон/драконид/нежить): бонусы статов + пассивка (эффект с `tag:race`). Творческие — `race_change {name, bonus, passive}` (бонус хранится в `race_bonus`).
- **6 вшитых классов** (Воин/Лучник/Маг/Вор/Жрец/Бард): при смене выдаётся стартовый навык; творческие — `class {name, skill}`. Ранги F<E<D<C<B<A<S<SS<SSS<Z<ZZ<ZZZ<G (`RANK_ORDER`), эволюция `class_evolve`, мультикласс `secondary_class`.
- **9 вшитых профессий** (Кузнец/Алхимик/…/Книжник): постоянный бафф стата (`profession_buff`), творческие — `profession {name, buff}`.
- **Профессии растут от действий — НО решает рассказчик (сессия 19)**: `player.actions {действие: счётчик}` по-прежнему копятся директивой `player.actions`, но авто-смена `check_profession_advance` больше НЕ вызывается в игровом конвейере (routers/core.py) — она осталась как доступный хелпер (`mechanics.py`), а решение о смене/изобретении профессии/класса/титула полностью на рассказчике (правило 19 промпта). Уровень/статы/репутация — тоже творческие: `player.level` для сюжетного роста, `player.stats` аддитивно, `reputation` — смысловые отношения.
- **Скрытые классы/расы/профессии/навыки** (сессия 5): правило 19 в промпте — рассказчик может выдавать творческие сущности за особые цепочки действий/ритуалы/испытания без афиширования условий; системные сообщения хода становятся «условием получения» карточки (meta.origin).
- **Навыки**: `skills {имя: {rank, kind, desc, mp_cost}}` — активные/пассивные, ранги; `effective_stats(p)` = база + моды эффектов (для проверок и формата состояния).
- **Эффекты**: постоянные/временные, стаки (урон×стаки в тике), моды к статам (UI и `format_state` показывают эффективные статы), тик в начале хода (`tick_effects`) — при перегенерации НЕ задваивается (снапшот). Тикают оба ресурса: HP (`damage`/`heal`) и MP (`mp_damage`/`mp_heal`, сессия 40). Временный эффект сообщает остаток каждый ход (`⏳ «…» осталось N ходов`, сессия 40 п.15) — раньше системка была только при уроне/лечении, и «тики молча» выглядело как «эффект не работает». Бессрочный (`turns` −1) эффект, у которого в `desc` назван срок, помечается мастеру — системкой при наложении и строкой в `format_state` (`effect_needs_turns`, сессия 40, п.7): движок срок сам не назначает и текст не читает (закон 3). Имя-синоним уже висящего эффекта (`«Стабилизация фрактала»` → `«Стабилизация родового канала»`) — тот же сигнал мастеру: системка при наложении + пометка в `format_state` (`find_similar_effect`, сессия 40, п.8); слияние/переименование — всегда на мастере.

### Память — 5 слоёв (никто и ничто не забывается)
1. **Краткосрочная**: последние несвёрнутые обмены в пределах бюджета (таблица `events`, роли player/narrator). **Бюджет per-world**: `world_recent_budget(world)` = `context_tokens − CONTEXT_OVERHEAD(2600) − max_tokens` (мин. 400). Размер контекста задаётся в настройках мира (ползунок «Размер контекста», `gen_settings.context_tokens`, по умолч. `CONTEXT_TOKENS`=32768 из .env); не превышать n_ctx модели (llama.cpp = 8192, облачные — до 32k+).
2. **Сводки**: при переполнении окна старые события сворачиваются LLM в 2–5 предложений (`summarize_and_compress`), роль `summary`, события помечаются `folded=1`.
3. **Векторная (RAG)**: ВСЕ обмены (`index_exchange`), сводки (`index_summary`), карточки (`index_entities`) индексируются в свою ChromaDB (метаданные `world_id`!). Поиск `retrieve_memory`: эмбеддинг запроса → `chroma_client.query(where={"world_id":...})` → гибрид BM25+косинус (`embeddings.hybrid_rerank`, вес BM25 из `HYBRID_WEIGHT_BM25` .env/админки) → облачный реранкер → top-K. **Локальный оффлайн-эмбеддинг**: провайдер `local` (FastEmbed, `paraphrase-multilingual-MiniLM-L12-v2`, 384-dim, кэш `data/fastembed`) — полный оффлайн без ключей/интернета. Т.к. Chroma держит одну размерность на коллекцию, коллекция выбирается **по фактической размерности входящих векторов** (`chroma_client.collection_name_for_dim`): облачный 4096 → `text_game_memory`, локальный 384 → `text_game_memory_local`. Это устойчиво к per-world переключению провайдера (глобально routerai, мир на local и наоборот). `delete_by_*` чистят из обеих коллекций. Порог косинуса для local ниже (`COSINE_THRESHOLD_LOCAL`, дефолт 0.20), т.к. fastembed даёт разрежённые близости; векторы нормируются при вставке (`chroma_client.add`) и запросе.
4. **Карточки сущностей** (таблица `entities`): NPC, локации, фракции, квесты, предметы, события — каждый с `summary` (статус сейчас), `relationship` (отношения с игроком), `bio` (накопленная история), `meta` (JSON: alive/location/faction). После каждого хода LLM-архивариус обновляет их (`update_entity_cards`, JSON-ответ). В контекст попадают релевантные карточки (`select_relevant_entities`: текущая локация, NPC рядом, активные квесты, явные упоминания в действии). `name` карточки — ВСЕГДА человекочитаемый, а не внутренний id: `memory.resolve_card_name` (сессия 40, п.9) берёт имя из ответа архивариуса → из состояния мира (`card_name_from_setting`) → прежнее, и машинному id (`player`, `trail_to_outpost`) НЕ позволяет перетереть уже человекочитаемое имя; старые карточки чинит само-исцеление при старте (`memory.repair_machine_card_names` — правит только там, где имя ЗНАЕТ состояние мира).
5. **Карточки знаний** (таблица `entities`, kinds `race/class/profession/skill/effect/item`): детерминированно (без LLM) после каждого хода `ensure_knowledge_cards` фиксирует созданные расы/классы/профессии/навыки/эффекты и предметы инвентаря с их механикой (бонусы/пассивки/баффы/ранги/стаки/моды); на новых карточках из системных сообщений хода пишется `meta.origin` — **условие получения** («🎖 Изучен навык…», «⚒ Профессия: — → Кузнец…», «🎒 Получено: …») — чтобы рассказчик не противоречил себе; индексируются в Chroma (мета `entity_kind`) и выбираются `select_relevant_entities` (бонус приоритета за знание игроком).
6. **Лор мира (библия вселенной)** (таблица `lore`): большие статьи о мире (история, география, системы, фракции, термины, `tags`, `is_core` — якорные, `source` = theme/custom/user). Сидинг при создании мира: из темы-сюжета (статьи `lore_articles`/`lore_text` в файле сюжета, см. `backend/plots.py`) или из своего сюжета (`custom_lore` / `story_plots.lore`, разбор по `## Заголовок` → отдельные статьи). Чанкинг `_chunk_lore` (по абзацам/предложениям, ~550 токенов) + индексация в Chroma (`index_lore_entry`, kind=`lore`, мета `lore_id`/`title`, переиндексация при правке, `$and`-where). Отдача в промпт: `retrieve_lore` → якорные статьи (всегда, сжато) + RAG-чанки по действию игрока (`LORE_RAG_K`) + фолбэк свежими статьями при выключенном RAG; бюджет `LORE_TOKEN_BUDGET` (дефолт 900) — есть константа `lore_rag_k`. Блок `[ЛОР МИРА — факты вселенной…]` в `build_messages`; правила 27–29 в system prompt (26 — фракции): «не противоречь лору, не выдумывай канон; лор сжатый — достраивай в стиле». CRUD: `backend/routers/lore.py` (`GET/POST /api/worlds/{id}/lore`, `PATCH/DELETE .../lore/{id}`, `GET .../lore/search?q=`), вкладка «Лор» в UI (рендер/модалка/поиск), поле лора в своём сюжете (модалка «Мои сюжеты» + `custom_lore`).
+ **Состояние мира** (`worlds.setting` JSON — всегда в system prompt через `format_state`). Здесь же: `player.identity` — всегда заполненная биография персонажа «кто я» (имя/возраст/происхождение/занятие/положение); если игрок дал «Свой зацеп» — это он, иначе генерируется `narrator.generate_identity` по теме/лору при создании мира; показывается рассказчику каждый ход (`format_state`) и игроку в сайдбаре «Персонаж». **Богатый старт первой генерации (сессия 15)**: доп. LLM-вызов `narrator.generate_character` (см. ниже) заполняет при создании мира не только биографию, но и роль (раса/класс/профессия со стартовыми навыками/бафф/пассивкой через движок директив), уровень, распределённые характеристики (НЕ все 10), навыки, титулы и персонализированный инвентарь с описаниями — согласованные с миром/лором/биографией (напр. бессмертный маг 900 лет не стартует новичком); применение — `narrator.apply_character`; при неудаче — фолбэк на `generate_identity`. В UI: блок «🧙 Персонаж» вкладки «Состояние» (после «Характеристик»): имя + полная биография + раса/класс/профессия/навыки/титулы/репутация/действия явными параметрами с описаниями; предметы инвентаря кликабельны — модалка с описанием (`showItem`). Стартовая локация — из `theme.start_location` (напр. «Чикаго, Эпидемия кошмаров» для Ключей Пангеи — это КАНОН темы, а не зашитый персонаж).

### Формат промпта рассказчика (`build_system_prompt`)
Персона рассказчика (из `narrators.prompt` мира) → тема/жанр/сложность/перспектива/язык → правила рассказчика (живой мир, логика, не решать за игрока) → описание формата `<<ENGINE>>` → текущее состояние мира. Модификаторы из тем (сюжеты из `plots/`, жанры `GENRE_HINTS`).

### Рассказчики (`narrators`, сменные персоны)
- Таблица `narrators(id, name UNIQUE, desc, prompt, is_preset, created_at, updated_at)`; 8 предустановленных сеются идемпотентно (`db.seed_narrators` — в стартовом проходе `app.self_heal()`, а НЕ на импорте app.py: A13, аудит 41; файлы `plots/narrators/*.js`). `GET /api/narrators` досеивает пустую таблицу сам (дешёвый `INSERT OR IGNORE`), чтобы каталог не пустовал в первые миллисекунды после запуска.
- **Пресеты живут файлами** в `plots/narrators/*.js` (чистый JSON: `name`/`desc`/`prompt`) — загрузчик `backend/narrators_loader.py` (сканирует при старте, `ensure_fresh` по mtime при GET /api/narrators; при изменении — пересид в БД `db.seed_narrators` идемпотентно по `name`). `narrator.NARRATOR_PRESETS` — это список из файлов (старый хардкод в `narrator_data.py` удалён).
- **Рекомендуемый рассказчик сюжета**: в JSON сюжета можно задать опц. поле `narrator` (имя пресета). `plots.py::_theme_from_plot` прокидывает его в тему (`theme["narrator"]`), `GET /api/themes` резолвит имя → `narrator_id` (по `db.list_narrators()`); фронт при выборе темы авто-подставляет его в селект рассказчика (пользователь может сменить).
- `worlds.narrator_id` — рассказчик мира (NULL = дефолтный, первый). Персона попадает в `build_system_prompt(world, setting, persona=...)`, а также в `generate_opening` и `narrate_roll`.
- CRUD: `GET/POST /api/narrators`, `PATCH/DELETE /api/narrators/{id}`. Удаление запрещено (409), если рассказчик используется миром. Смена — `POST /api/worlds/{id}/settings {narrator_id}`.
- Архивариус карточек и сводки — отдельные системные персоны, рассказчиком НЕ управляются.

### Провайдеры (основная модель / эмбеддинги / реранкер / TTS)
- `config.py::PROVIDER_OPTIONS` — реестр: `main` (llamacpp|ollama|openai_compat), `embedding` (routerai|openai_compat|none), `rerank` (routerai|openai_compat|none), `tts` (piper|kokoro|edge|none).
- Глобальные настройки — `.env` ИЛИ **админка** (`GET/POST /api/admin/settings`, страница `/admin`): таблица `admin_settings` (ключи в верхнем регистре, как env). Приоритет: env процесса → админка → .env. Пустое поле = сброс к .env; API-ключ при пустом поле не меняется. `invalidate_config()` сбрасывает кэш после сохранения. **B2 (аудит 41): оба метода админки закрыты до localhost** (`ratelimit.require_local`; чужой адрес → 403) — админка переписывает провайдеров и `MAIN_BASE_URL`, открывать её сети = подарить перехват промптов и ключей; сознательное исключение — `ADMIN_ALLOW_LAN=true` в `.env` (в `hidden_admin_keys`, самой админкой не включается). Все «дорогие» роуты (ход/создание мира/suggest/vision/providers/память/лор/карточки/импорт/TTS/админка) стоят под rate-limit'ом — реестр `ratelimit.SCOPES`, вешается `Depends(guard_for(scope))`; факт наличия сторожит реестр-тест по зависимостям самого приложения (`tests/test_session55_ratelimit_routes.py`).
- **Админка читается отдельным sqlite-соединением** (`backend/admin_settings.py::read_overrides`) — НЕ через db.py: db._db() вызывает get_config(), а рекурсия config→db вешает сервер (нереентерабельный Lock). Не ломать! Приоритет: env процесса → админка → .env.
- Живость основной модели проверяется ОДНОЙ функцией: `llm.probe(provider)` → `(up, needs_key, detail)`; `llm.check_available()` — её же обёртка над `probe` (A12, аудит 41: раньше `routers/system.py` держал ВТОРОЙ критерий — голый `GET {base}/models` без заголовка ключа и «жив» = ровно 200, из-за чего на llama.cpp с `--api-key`/облачном шлюзе мир игрался, а плашка статуса врала «LLM ✗»). Критерий: «жив» = ответ < 500 (401/403/404 — живой сервис), ключ всегда шлём в `Authorization`, `needs_key` отдельно отличает «не отвечает» от «требует ключ». При создании мира недоступная модель → **503**, мир не создаётся.
- Per-world переопределения — `worlds.provider_settings` (JSON `{kind: {id, base_url, api_key, model, enabled}}`), меняются через `POST /api/worlds/{id}/providers`; пустой api_key/base_url/model = «оставить как есть» (ключи маскируются).
- Резолв: `config.get_provider(kind, overrides)` → dict `{id, name, base_url, api_key, model, enabled, needs_key, needs_model}`; `resolve_world_providers(ws)` → все три. LLM/эмбеддинги/реранкер принимают `provider=` (см. `llm.complete/stream_chat`, `embeddings.embed_batch/rerank_results`).
- Если эмбеддинги `none`/без ключа — `retrieve_memory` тихо возвращает пусто (RAG выключен, игра живёт). Реранкер `none` или `enabled:false` — гибрид BM25+косинус без облачного реранка.

### Озвучка (TTS, `backend/tts.py`)
- Провайдеры: **piper** — локальный (sherpa-onnx, голоса `ru_RU-ruslan/irina/dmitri/denis-medium`, скачиваются из релиза k2-fsa/sherpa-onnx tts-models, ~30–70 МБ, качество среднее); **kokoro** — локальный Kokoro-82M (~350 МБ, без русского, для en-миров); **edge** — ⭐ **стандарт/рекомендован**: облачный Microsoft Edge TTS (`edge-tts`, лучшие русские голоса ru-RU-DmitryNeural (муж., стандарт)/SvetlanaNeural, бесплатно, нужен интернет); **none**. Дефолты: провайдер `edge`, голос `ru-RU-DmitryNeural`. Edge требует явный знак в `rate` (`+0%`, а не `0%`) — нормируется в `tts._synth_edge`.
- Глобальные настройки — `.env`/админка (`TTS_ENABLED/PROVIDER/VOICE/RATE/AUTO_PLAY/CACHE_*`); per-world — `worlds.tts_settings` JSON {enabled, provider, voice, rate, auto_play}, `POST /api/worlds/{id}/tts/settings`; пустые поля = «по умолчанию (глобально)».
- Синтез — **фоновый** (`tts.ensure_event_audio`, не блокирует ответ): событию рассказчика ставится `tts_status=1`, аудио кэшируется по хешу (текст+голос+скорость) в `data/tts/cache/` (+ таблица `tts_cache`); статус события 2=готово, −1=ошибка (повтор — `POST .../events/{eid}/tts/retry`).
- UI: кнопка 🔊/⟳/⚠ у ответов рассказчика, поллинг готовности, авто-плей (опция), настройки во вкладке «Настройки» («Проверить голос», «Скачать голос»), глобально — админка.
- Эндпоинты: `GET /api/tts/status`, `POST /api/tts/test` (base64), `POST /api/tts/download`, `GET /api/worlds/{id}/events/{eid}/audio`, `.../tts/status`, `.../tts/retry`.
- Правила: синтез только в фоне (не блокирует ответ); озвучивается только `final_text` (без механики); `TTS_MAX_CHARS` (2400) режет текст по предложениям.

### Автогенерация контента
- Создание мира: `generate_opening` — LLM пишет вступительную сцену по теме (с инжектом лора и вплетением персонажа, см. сессия 14).
- **Баг-хант сессии 40 (мир «Новый мир»), п.3–п.16** — живые правила от него уже
  разложены по этому файлу (ход: `tick_time`/`_env_last_turn`; карточки: `resolve_card_name`;
  эффекты: `effect_needs_turns`/`find_similar_effect`; флаги и статистика: `flag_titles` и
  `PROGRESS_LABELS`; фронт: `msgClass`/`adoptPlayer`/`travelActionText`/`scrollToSeq`). Сами
  эссе «симптом → причина → цена» перенесены в `AGENT_ARCHIVE.md` («Сессия 40»): здесь им не
  место, потому что этот файл читают ПЕРЕД правкой, а не вместо неё.
- **Сюжеты-миры живут файлами в папке `plots/`** (НЕ хардкодом): `plots/system/` — комплектные «стандартные» сюжеты, `plots/user/` — сюжеты игрока. Каждый файл — чистый JSON (расширение `.js`) по полной схеме `PLOTS.md` (`metadata`/`lore_articles`/`lore_text`/`factions`/`starting_state`/`story`/`plot_text`/`handoff_directives`).
- **Загрузчик `backend/plots.py`**: при старте и по кнопке «🔄 Обновить сюжеты» (`POST /api/plots/reload`) сканирует обе папки, строит тему-обёртку для каждого сюжета и отдаёт в `narrator.THEMES`/каталог. `GET /api/themes` сам проверяет mtime файлов (`ensure_fresh`) — новый/правленый сюжет подтягивается даже без кнопки/рестарта. `id` темы = поле `id` файла или транслитерация имени файла; `user/` переопределяет `system/` при совпадении id.
- **При создании мира из сюжета** (`worlds.py::create_world`, ветка `else`): тема-обёртка даёт стиль/жанр/завязку/лор; `narrator.apply_plot_start` применяет `starting_state` (локации/NPC/магазины/фракции/квесты/флаги/время/погода/золото/инвентарь). Роль игрока (раса/класс/статы/уровень) **не из сюжета** — её генерирует `generate_character` (PLOTS.md п.5.1).
- **Миры не зависят от файлов сюжетов**: при создании в `setting["_theme_snapshot"]` копируется тема-обёртка, а `narrator._world_theme(world, setting)` использует её как фолбэк, если файл сюжета позже удалён/отредактирован → мир живёт по данным на момент создания.
- **Автопроверка сюжетов**: новый/правленый файл сюжета обязательно прогонять через `scripts/check_plot.py plots/<folder>/<file>.js` — ловит призрачные id (relations/connections/key_quests/key_npcs/next_quest_id), дубли `new_locations` (локация уже в старте), `false`-флаги в `key_flags_to_set`, недопустимые статусы квестов/связей фракций, рассинхрон `lore_articles`↔`lore_text`. Правила закреплены в PLOTS.md (п.4.1/4.2/4.4/5.3/9/12).
- Подсказки жанров — `GENRE_HINTS` (33 шт) в `narrator_data.py`.

> **Два разных лимита токенов (НЕ путать!):**
> - **`MAX_TOKENS` (в `.env`/админке/настройках мира, стандарт 2000)** — лимит **КАЖДОГО обычного хода игры** (ответ рассказчика на действие игрока): применяется через `routers/core.py::_gen_params` → `gen_settings.max_tokens`.
> - **Лимит открытия мира** — `OPENING_MAX_TOKENS = 2400` в `backend/character_generator.py::generate_opening` (в `narrator.py` — только реэкспорт фасада). Отдельный разовый вызов при создании мира, настроек мира **не читает**. 2400 — с запасом под reasoner-модели (часть лимита уходит на reasoning); там же `temperature = default_temp + 0.05`, до 3 повторов (при пустом ответе ИЛИ оборванном вступлении, сессия 40 п.3) и фолбэк на `theme.opening`.
> A11 (аудит 38): пустое вступление больше не роняет создание мира и не рождает пустое сообщение (`db._add_event` на пустом тексте бросает `ValueError` — внятная ошибка вместо голого `IntegrityError`).
> Т.е. настройка 2000 НЕ влияет на длину вступления (там свои 2400), а 2400 НЕ влияют на игровые ответы (там из настроек). Увеличивая одно, не трогаешь другое.

## 🗄 СХЕМА БД (backend/db.py)

- `worlds(id, name, theme, genre, difficulty, perspective, language, custom_hook, setting JSON, gen_settings JSON, narrator_id, provider_settings JSON, snapshot TEXT, created_at, updated_at)` — `genre` может содержать **несколько жанров** через запятую (мультивыбор при создании мира, `POST /api/worlds {genres: [...]}`); `theme='custom'` = **свой сюжет** (`custom_plot` — текст / `plot_id` — сохранённый сюжет); `snapshot` = состояние до последнего хода для отката при перегенерации.
- `events(id, world_id, seq, role[narrator|player|system|dice|summary], content, folded, feedback[-1|0|1], ts)` — полная история, индекс `(world_id, seq)`
- `saves(id, world_id, name, seq, setting JSON, created_at)` — слоты сохранений
- `lore(id, world_id, title, content, tags, is_core, source[theme|custom|user], created_at, updated_at)` — статьи лора мира (библия) — см. «Память, слой 6»

## 💻 СОГЛАШЕНИЯ ПО КОДУ

- Python: `from __future__ import annotations`, типизация, UTF-8.
- **SQLite — через `backend/db.py` на aiosqlite** (сессия: миграция на асинхронный драйвер): единственное соединение aiosqlite живёт на выделенном фоновом asyncio-цикле (поток `aiosqlite-loop`), а публичный API модуля остался **синхронным** — каждая функция ставит корутину в очередь фонового цикла (`_run` + `asyncio.run_coroutine_threadsafe`) и ждёт результат. Сигнатуры/семантика нетронуты, `transaction()`/RLock/`_tx_depth` прежние. `_maybe_commit` — корутина (внутри корутин коммит напрямую `await conn.commit()`, а НЕ через `_run` — иначе дедлок на том же цикле). `db.close()` корректно закрывает соединение/цикл в тестах/скриптах. **Белый список полей записи** (D11, аудит 41): `update_world(**fields)` пишет только колоночные имена (`name/setting/gen_settings/narrator_id/provider_settings/snapshot/tts_settings`) — это единственная защита от подстановки имени колонки в SQL, поэтому лишние ключи и дальше НЕ попадают в `UPDATE`; но молча они уже не глотаются: на каждый лишний ключ — `log.warning("update_world(world N): неизвестное поле ...")`, иначе опечатка в имени поля выглядела бы как «записали и ничего не случилось» (правило 14).
- **Разделение слоёв**: `db.py` — ЧИСТО доступ к данным (никакой бизнес/презентационной логики: без форматирования, без подписей ролей, без сборки текстов). Бизнес-логика живёт в `routers/*` (а для механики — `mechanics.py`, для памяти/промптов — `narrator.py`). Если нужен отформатированный вывод (напр. экспорт) — `db` отдаёт сырые данные, а сборку текста делают в роутере (пример: `db.export_data` → `routers/worlds.py::render_export_history`).
- **Атомарные группы записи**: `db.transaction()` — события хода + состояние мира пишутся одной транзакцией. `_lock` удерживается **на всё время тела** (A9, аудит 38: раньше лок снимался сразу после `BEGIN IMMEDIATE`, и запись из другого потока вписывалась в чужой открытый `BEGIN` — при откате она исчезала из БД вместе с уведомлением живого чата, при чужом коммите — рассылалась с чужим контекстом). Тело блока ОБЯЗАНО быть синхронным (без await) — инвариант проверяет `tests/test_session38_layers.py::test_no_await_inside_transaction_body`. Мутации состояния хода (карточки знаний → дневник → ружья Чехова) идут ДО единой `update_world` в конце транзакции (A1). **Таймаут внутри группы дозакрывает транзакцию сам (D12, аудит 41):** `_tx_depth` уменьшается ПЕРЕД вызовом `_run(_commit_now)`, поэтому при «БД не ответила за `_RUN_TIMEOUT`» отменённая корутина коммита оставляет единственное соединение в открытом `BEGIN IMMEDIATE` — строки откатанного хода оставались видны этому же соединению, буфер `_pending_events` уносился в шину живого чата следующим коммитом (фантомы), а файл держал write-lock. Теперь признак незакрытого BEGIN ведёт флаг `_tx_open` (`_begin_now` ставит, `_commit_now`/`_rollback_now` снимают), и `_run` при таймауте с `_tx_open and _tx_depth == 0` зовёт `_rescue_transaction`: `log.error` с контекстом + явный `_rollback_now` + очистка буфера (отказ самого отката — тоже `log.error`, правило 14; исключение таймаута не подменяется). Ложных откатов нет: вне `transaction()` BEGIN не открыт, поэтому спасение не срабатывает.
- **Фоновые задачи**: LLM-проходы — `bg.submit(name, factory, priority=…, world_id=…)` (не блокируют ответ); короткие «огонь-и-забыл» — **`bg.spawn(coro, name=…)`**, а НЕ `asyncio.get_event_loop().create_task(...)`: asyncio хранит задачи слабыми ссылками, и брошенную задачу мог собрать GC посреди игры (D6/RUF006 — симптом «карточка/индекс не появились, в логе ничего»). `get_event_loop()` deprecated в 3.12 и ошибка в 3.13: в async-коде `get_running_loop()`, в тяжёлых синхронных вызовах — `asyncio.to_thread`.
- SSE streaming в `backend/routers/worlds.py::action_stream` (раньше — в app.py): worker кладёт токены в `asyncio.Queue`, генератор `gen_stream()` отдаёт `event: token` / `event: result` (один в конце) / `event: error`. Слэш-команды через стрим отдают **тот же** `event: result` (A7: фронт слушает только token/result/error, `event: done` терял ответ команды).
- **Известные фиксы (не наступить снова):**
  - (отчёты сессий 30 и 22 перенесены в `AGENT_ARCHIVE.md`, «Известные фиксы»: карточки

### Инварианты (легко наступить снова — проверять при доработках)

1. **`meta.turn` — метка СОБЫТИЙ ХОДА** (= seq действия игрока). Новый агент/директива,
   пишущие события в ход, обязаны ставить метку, иначе `↻` их не заменит. Фоновые события
   мира метку НЕ носят — `↻` их стирать не должен.
2. **Фоновая запись в setting — только через `_bg_may_write(...)`** (ядро) или проверку
   `bg.is_regenerating()` (память), СРАЗУ после перечитывания состояния: `await` между
   чтением и записью = гонка. Нельзя возвращаться к `s`/`world`, снятым в начале функции.
   `POST .../divine` сверяется тем же механизмом с сессии 38 (A15) — иначе затирал ход, и с
   сессии 65 (D2) пишет результат ПОВЕРХ перечитанного `fresh` (директивы Провидения
   применяются повторно к нему, а не к снимку начала запроса).
   Любой НОВЫЙ способ менять setting из фона обязан проходить ту же сверку. Откат таймлайна
   (⏪ перемотка, загрузка сохранения) держит ТУ ЖЕ перемычку `_regen` через `bg.rewind_block`,
   а ход игрока занимает мир через `bg.turn_block` — без этого «перемотка» догоняется идущим
   ходом и мир сразу уезжает в будущее (аудит 41, A5). Занятый мир = честный 409, а не
   тихая порча прохождения.
3. **Синхронизация «карточки → setting»**: один распарсенный объект, одна запись в конце.
   Парсить `world["setting"]` по месту в каждом блоке нельзя — следующий блок затрёт
   предыдущий (проверено: терялись квесты и NPC).
4. **Состояние хода пишется ОДНИМ `update_world` ПОСЛЕ всех мутаций** (карточки знаний →
   дневник → ружья Чехова): мутация после записи теряется для следующего хода — так
   «ружья Чехова» были мертвы две сессии (A1).
5. **Новый формат вывода модели в `split_engine`** добавляется в `_iter_json_objs` /
   `_is_engine_obj`, а не отдельным регэкспом; `ENGINE_KEYS` пополняется из `DIRECTIVE_CHAIN`
   сам (`roll`/`dice` — явно).
6. **`ensure_player_schema`** — единственная гарантия числовых осей игрока (`hp/mp/gold/
   level/inventory`): `apply_directives` читает `p["hp"]` напрямую. Молча чинить кривые
   данные вне схемы нельзя.
7. **`db._run` бросает `RuntimeError` из потока цикла БД**: фоновым корутинам на этом цикле
   нельзя вызывать синхронный API `db.*` (выполняй корутины `_*` напрямую или через очередь).

27. **«Дорогой» эндпоинт не бывает без лимитера** (B2, аудит 41). Любой роут, который зовёт
    LLM, облачные эмбеддинги/реранкер, синтез речи, скачивание моделей, полную переиндексацию
    памяти или меняет глобальные настройки, обязан висеть под `Depends(guard_for(scope))`, а
    имя scope — существовать в реестре `ratelimit.SCOPES` (свои значения на каждый роут,
    лимиты ЩЕДРЫЕ: цель — скрипт/заломанная кнопка/чужой в сети, а не игрок). У игры нет
    авторизации, а `GAME_BIND` может быть не loopback, поэтому: (а) чужому адресу лимиты
    режутся в `REMOTE_FACTOR` раз (`scope_limits(scope, host)`), (б) `/api/admin/settings`
    дополнительно закрыт до localhost через `ratelimit.require_local` — админка переписывает
    `MAIN_BASE_URL` и ключи, а rate-limit от подмены адреса не спасает; единственный способ
    открыть её наружу — `ADMIN_ALLOW_LAN=true` в `.env`, и ключ лежит в `hidden_admin_keys`,
    чтобы админка не разблокировала саму себя. Новый роутер с guard'ом вешается меткой
    `_rl_scope` (её ставит сам `guard_for`) — реестр-тест читает зависимости маршрутов
    приложения, поэтому молча забыть лимитер на «дорохом» пути нельзя, как и выдуманный scope.
    Счётчики лимитера (D3, аудит 41) — обычные словари, а не `defaultdict`: чтение чужого ключа
    не создаёт запись, запись появляется только в `allow()`, а ключи, к которым не обращались
    дольше `_STALE_AFTER`, выметает амортизированная `_prune()` (не чаще раза в `_PRUNE_AFTER`).
    Ключей теперь `scope × адрес`, после B2 их 19 роутов на каждый клиент, и карта без чистки
    росла бы всю жизнь сервера. Тот же закон действует в `bus.py` (D10, аудит 38): in-memory
    реестр «кто чем пользуется» обязан уметь и терять пользователей.
28. **Ни одно пользовательское текстовое поле API не бывает без границы длины** (B3, аудит 41).
    Границы живут одним местом — константы `backend/schemas.py` (`PERSONA_MAX`, `PLOT_MAX`,
    `LORE_TEXT_MAX`, `HOOK_MAX`, `COMPLAINT_MAX`, `ACTION_HARD_MAX`, `CARD_*`, `NAME_MAX`, …)

    фактическими текстами: самый длинный пресет персоны 2 КБ при лимите 20 КБ), иначе первый же
    сюжет упрётся в 422. Причина не в «гигиене»: один POST с мегабайтным текстом раньше
    оседал в SQLite и уходил в промпт КАЖДОГО хода мира. Мягкий лимит действия игрока остаётся

    больше (`ACTION_HARD_MAX` — только жёсткий потолок тела запроса). Дополнительно: персона,
    которая уже лежит в базе (старый мир, импорт дампа, правка файла пресета), не может раздуть
    промпт — `narrator.clip_persona`/`PERSONA_TOKEN_BUDGET` режут её при сборке system-промпта

    границе — 422 с человекочитаемым `detail` (в `app.py` висит обработчик `RequestValidationError`:

    (правило 14). Новое текстовое поле схемы = `Field(max_length=…)`, а не «как-нибудь порежем в
    роутере».
